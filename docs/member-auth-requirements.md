# 企業会員ログイン・会員判定 要件定義書

作成日: 2026-05-04  
対象機能: 企業会員限定 学生データベース  
対象サイト: 近世 KINSEI 公式 HP

## 1. 目的

企業会員のみが学生データベースの詳細情報を閲覧できるようにする。

一般公開ページでは学生の一部情報だけを見せ、価値観、志望理由の深掘り、意思決定の軸、将来像、面談リクエストなどはログイン済みかつ有効な企業会員に限定する。

## 2. 決定事項

今回の初期実装では、以下の方針で進める。

- アカウント単位: 企業ごとに 1 アカウント
- アカウント登録: 運営が企業情報と担当者メールアドレスを登録する
- パスワード設定: 企業担当者が招待リンクまたはパスワード設定リンクから自分で設定する
- 認証方式: メールアドレス + パスワード
- 会員判定: 初期実装から導入
- 契約管理: 本システム内で決済や契約締結は行わず、外部で確認した契約状況を運営が登録する
- 技術方針: Next.js + Supabase Auth + Supabase Postgres
- DB アクセス: Supabase JS / `@supabase/ssr`
- 学生側アカウント: MVP では作成しない
- 面談リクエスト: 初期は企業から運営への送信

## 3. ユーザー種別

### 3.1 未ログインユーザー

ログインしていない一般ユーザー。

できること:

- 公開学生データベースの閲覧
- 学生の簡易プロフィール閲覧
- 企業会員問い合わせ導線の利用

できないこと:

- 学生の詳細プロフィール閲覧
- 会員限定学生データの取得
- 面談リクエスト送信

### 3.2 企業会員

運営が登録した企業アカウントでログインするユーザー。

できること:

- ログイン
- 会員限定学生一覧の閲覧
- 学生詳細プロフィールの閲覧
- 面談リクエスト送信
- ログアウト

制約:

- 1 社につき 1 アカウント
- アカウント登録、停止、再開は運営が行う
- ログイン用メールアドレスは企業側が既に保有している担当者メールアドレスを使う
- パスワードは企業担当者が自分で設定する
- 契約状態が有効な場合のみ会員限定情報を閲覧できる

### 3.3 運営管理者

近世 KINSEI 側の管理者。

できること:

- 企業情報と担当者メールアドレスを登録
- 企業担当者へパスワード設定リンクまたは招待リンクを送付
- 企業プロフィールを登録、編集
- 会員ステータスを変更
- 必要に応じてアカウントを停止
- 面談リクエストを確認

運営担当者はエンジニアではない前提のため、将来的には専用管理画面から操作できるようにする。
管理画面の詳細は `docs/admin-requirements.md` に定義する。

## 4. 会員ステータス

企業アカウントには会員状態を持たせる。

| ステータス | 意味 | 会員限定閲覧 |
| --- | --- | --- |
| `active` | 契約中 | 可 |
| `trial` | トライアル中 | 可 |
| `past_due` | 支払い確認待ち | 不可 |
| `suspended` | 停止中 | 不可 |
| `cancelled` | 解約済み | 不可 |

MVP では `active` と `trial` のみ閲覧可能とする。

契約やサブスクリプションは本システム内では処理しない。
運営が外部で確認した契約状況を管理画面に登録し、そのステータスを閲覧権限の判定に使う。

## 5. 企業アカウント登録フロー

### 5.1 基本方針

企業アカウントは運営登録制とする。
誰でも自由に会員登録できる一般登録フォームは MVP では設けない。

ログイン用メールアドレスは企業側が既に持っている担当者メールアドレスを使う。
本システムはメールアドレスを発行しない。

### 5.2 推奨フロー

1. 運営が外部で契約、サブスクリプション、トライアル提供状況を確認する
2. 運営が管理画面で企業名、担当者名、担当者メールアドレス、契約ステータスを登録する
3. システムが Supabase Auth に企業担当者のユーザーを作成する
4. システムが管理画面にログイン設定リンクを表示し、運営が既存チャットで企業担当者へ共有する
5. 企業担当者がリンク先で自分のパスワードを設定する
6. 企業担当者がログインする
7. 会員ステータスが `active` または `trial` の場合のみ会員限定学生 DB を閲覧できる

### 5.3 パスワード取り扱い

- 運営は企業のパスワードを知る必要がない
- 管理画面に企業パスワードを保存、表示しない
- ログイン設定リンクには有効期限を設ける
- リンク期限切れ時は運営が再発行できる
- 企業側のパスワード忘れにはパスワードリセット導線で対応する

### 5.4 リンク共有の運用

企業との契約・連絡は既存チャットで進んでいる前提のため、初回案内メールは送信しない。
管理画面で発行したログイン設定リンク、またはチャット用メッセージを運営がコピーして共有する。

## 6. 認証・アクセス制御

### 6.1 ログイン

ログイン画面ではメールアドレスとパスワードを入力する。

成功時:

- 会員ステータスが `active` または `trial` の場合、会員限定学生データベースへ遷移する
- 会員ステータスが閲覧不可の場合、契約確認画面へ遷移する

失敗時:

- メールアドレスまたはパスワードが違う旨を表示する
- 詳細な失敗理由は出しすぎない

### 6.2 会員限定ページ保護

対象ページ:

- `/members/students`
- `/members/students/[studentId]`
- `/members/requests`

未ログインでアクセスした場合:

- `/login` へリダイレクトする
- ログイン後、元のページに戻れるようにする

ログイン済みだが会員ステータスが無効な場合:

- 詳細データは表示しない
- 契約確認または運営問い合わせ導線を表示する

### 6.3 データ取得制御

会員限定情報は HTML や JavaScript に埋め込まない。

学生詳細データは、ログイン済みかつ有効な企業会員であることをサーバー側で確認した後に返す。

## 7. Supabase データ設計

### 7.1 `companies`

企業情報と会員状態を管理する。

| カラム | 型 | 内容 |
| --- | --- | --- |
| `id` | uuid | 企業 ID |
| `auth_user_id` | uuid | Supabase Auth ユーザー ID |
| `company_name` | text | 企業名 |
| `contact_name` | text | 担当者名 |
| `contact_email` | text | 担当者メール |
| `membership_status` | text | 会員ステータス |
| `plan_name` | text | 契約プラン名 |
| `contract_status_note` | text | 外部契約状況の運営メモ |
| `contract_start_date` | date | 契約開始日 |
| `contract_end_date` | date | 契約終了日 |
| `next_check_date` | date | 次回確認日 |
| `created_at` | timestamptz | 作成日時 |
| `updated_at` | timestamptz | 更新日時 |

### 7.2 `students`

学生の公開プロフィールを管理する。

このテーブルには一般公開してよい項目のみを置く。

### 7.3 `student_member_profiles`

学生の会員限定詳細プロフィールを管理する。

有効な企業会員だけが参照できるように RLS で制御する。

### 7.4 `interview_requests`

面談リクエストを管理する。

| カラム | 型 | 内容 |
| --- | --- | --- |
| `id` | uuid | リクエスト ID |
| `company_id` | uuid | 企業 ID |
| `student_id` | uuid | 学生 ID |
| `request_reason` | text | リクエスト理由 |
| `preferred_method` | text | 希望形式 |
| `preferred_schedule` | text | 希望時期 |
| `status` | text | 対応状態 |
| `created_at` | timestamptz | 送信日時 |

## 8. セキュリティ要件

- Supabase の `service_role` キーはブラウザに出さない
- 会員判定はクライアント側だけで行わない
- 公開情報と会員限定情報の返却範囲を API 側で分ける
- Supabase の公開スキーマに置くテーブルは RLS を有効化する
- 会員ステータスはユーザーが編集できるメタデータに置かない
- 企業アカウント停止時は会員限定データ取得を拒否する
- 企業パスワードは運営が保持、表示、共有しない
- 招待リンクやパスワード設定リンクは期限付きにする
- 学生本人の掲載同意と公開範囲同意を別途管理する

## 9. 初期実装スコープ

### 実装する

- Next.js 化
- Supabase Auth 導入
- ログイン画面
- ログアウト機能
- 企業プロフィールテーブル
- 会員ステータス判定
- 会員限定ページのアクセス制御
- 学生詳細データの認証済み取得
- 面談リクエスト送信
- 企業担当者のパスワード自己設定フロー

### 後回しにする

- 企業ごとの複数担当者アカウント
- 企業側マイページ
- 決済連動
- パスワードリセット画面の作り込み
- 閲覧履歴
- お気に入り
- 社内メモ

## 10. 実装順序

1. 現在の静的 HTML を Next.js プロジェクトへ移行する
2. Supabase プロジェクトを用意する
3. 環境変数を設定する
4. `companies`、`students`、`student_member_profiles`、`interview_requests` のテーブルを作る
5. RLS と必要なポリシーを設定する
6. ログイン画面を作る
7. 会員限定ルートを保護する
8. 学生一覧と詳細データを DB から取得する
9. 面談リクエスト送信を DB に保存する
10. 運営が企業を登録し、企業担当者がパスワードを自己設定できる流れを作る
11. Vercel 環境変数を設定して本番確認する

## 11. 残タスク

- Supabase プロジェクト名を決める
- 学生データを実データで管理するか、最初はサンプル DB で始めるか決める
- 面談リクエスト送信時の通知先を決める
- 掲載同意書の項目を整理する
- 会員ステータス変更の運用担当者を決める
- 招待リンクを Supabase Auth の invite で行うか、独自のパスワード設定導線で行うか決める

## 1. 現状整理

### 1.1 サイト構成

現在のリポジトリは静的 HTML サイトとして構成されている。

- `index.html`: トップページ
- `sponsor.html`: スポンサー料金プラン
- `sponsors_list.html`: 協賛企業一覧
- `assets/images/`: 既存画像

CSS は各 HTML 内に Tailwind CDN とインライン設定で記述されており、現時点ではビルド工程、サーバーサイド処理、DB、認証機能は存在しない。

### 1.2 Git / GitHub 状況

- ローカルブランチ: `main`
- リモート: `origin https://github.com/King04022004/kinseiweb.git`
- `main` は `origin/main` と同期済み
- GitHub リポジトリ: public
- Vercel 連携情報: `.vercel/project.json` に `kinseiweb` プロジェクトとしてリンク済み

### 1.3 今回機能の実装上の前提

今回の「企業向け会員限定の学生データベース機能」は、単なる静的ページ追加だけでは完結しない。最低限、以下が必要になる。

- 企業アカウントのログイン機能
- 会員状態の判定
- 学生プロフィールのデータ管理
- 非会員向けの情報制限
- 会員限定詳細ページのアクセス制御
- 面談リクエスト送信機能

そのため、現在の静的 HTML のまま進める場合は「公開用の teaser ページ」までは実装できるが、本当の意味での会員限定閲覧には、Next.js などのアプリ化、または外部サービス連携が必要になる。

## 2. 目的

サブスク登録企業のみが、学生の詳細情報を閲覧し、面談リクエストなどのアプローチを行える状態を作る。

一般ユーザーには学生の一部情報だけを公開し、興味を持った企業に対して「続きを見るには企業会員登録が必要」という導線を設計する。

この機能の狙いは、単に学生情報を並べることではなく、以下の心理変化を作ることにある。

- 一覧ページ: 「この学生、少し気になる」
- 詳細ページ: 「この学生に会ってみたい」
- 会員登録導線: 「詳細を見られるなら登録したい」

## 3. 全体構造

本機能は大きく 2 つのエリアに分ける。

### 3.1 一般公開エリア

ログイン不要で誰でも閲覧できるエリア。学生の存在、雰囲気、志望方向性を見せる。

目的:

- 学生データベースの価値を外部に伝える
- 企業に「もっと知りたい」と思わせる
- スポンサー / サブスク登録への導線にする

想定ページ:

- `/students.html` または `/students/`
- 学生一覧
- 学生の簡易プロフィールカード
- 企業会員登録 CTA

### 3.2 会員限定エリア

ログイン済みの企業アカウントのみ閲覧できるエリア。学生の深い情報を表示し、面談リクエストに接続する。

目的:

- サブスク登録企業への提供価値を明確化する
- 学生の人柄、価値観、意思決定軸を深く伝える
- 企業と学生の接点創出につなげる

想定ページ:

- `/login`
- `/members/students`
- `/members/students/[studentId]`
- `/members/requests`

## 4. ユーザー種別と権限

### 4.1 一般ユーザー

ログインなしでアクセスするユーザー。

できること:

- 学生一覧の閲覧
- 学生の動画、名前またはイニシャル、学部・属性、志望業界の閲覧
- 会員登録 / 問い合わせ導線の利用

できないこと:

- 学生詳細プロフィールの閲覧
- 価値観、思考、志望理由の深掘りの閲覧
- 面談リクエスト送信

### 4.2 企業会員

サブスク登録済みで、運営からアカウントを発行された企業担当者。

できること:

- ログイン
- 学生一覧の完全閲覧
- 学生詳細ページの閲覧
- 面談リクエスト送信
- 将来的には閲覧履歴、お気に入り、社内メモの管理

### 4.3 運営管理者

近世 KINSEI 側の管理者。

できること:

- 企業アカウントの発行、停止
- 学生データの登録、編集、公開状態管理
- 面談リクエストの確認
- 企業ごとの利用状況確認

## 5. 一般公開エリア設計

### 5.1 学生一覧カードの表示項目

一般公開エリアでは、学生の魅力を完全には出し切らず、入口として機能する情報に絞る。

表示する項目:

- TikTok 埋め込み動画
- 名前またはイニシャル
- 学部
- 学年
- 属性タグ
- 志望業界
- ひとことキャッチコピー

非表示またはぼかし表示にする項目:

- 価値観・思考
- 志望理由の深掘り
- キャリア軸
- 意思決定の軸
- 将来像
- 詳細プロフィール
- 面談リクエストボタン

### 5.2 情報制限 UI

学生カード内に、会員限定情報の存在を見せるためのロック表示を置く。

例:

- 「価値観・思考」欄をぼかし表示
- 「志望理由の深掘り」欄にロックアイコン
- 「続きは企業会員限定」ボタン
- 「企業会員になると、意思決定の軸・将来像・面談リクエストが利用できます」という短い補足

### 5.3 CTA

公開ページの主要 CTA は「お問い合わせ」ではなく、機能価値に合わせて具体化する。

推奨 CTA:

- 企業会員について相談する
- 学生データベースを閲覧したい
- サブスク登録について問い合わせる

リンク先:

- 初期: `index.html#contact`
- 将来: 専用フォーム `/company-contact`

## 6. 会員限定エリア設計

### 6.1 ログイン後の学生一覧

ログイン済み企業には、一般公開よりも詳細な一覧を表示する。

表示項目:

- TikTok 埋め込み動画
- 氏名
- 学部、学年
- 志望業界
- キャリア軸の要約
- 価値観タグ
- 面談リクエスト状態
- 詳細を見るボタン

検索・絞り込み項目:

- 学部
- 学年
- 志望業界
- 価値観タグ
- キャリア軸
- 面談希望可否

### 6.2 学生詳細ページ

詳細ページでは、企業が「会いたい」と判断できる材料をまとめる。

表示項目:

- 基本プロフィール
- 動画
- 自己紹介
- 志望業界
- 志望理由
- 価値観・思考
- 意思決定の軸

- 将来像

- 面談リクエストボタン

### 6.3 面談リクエスト

企業担当者が学生に直接連絡するのではなく、初期は「企業 → 運営」への送信にする。

理由:

- 学生個人情報を守りやすい

- 初期運用で柔軟に調整しやすい

- 企業 ID
- 企業名
- 担当者名
- 担当者メールアドレス
- 学生 ID
- リクエスト理由
- 面談希望形式
- 希望時期
- 送信日時

初期の送信先:

- Google Form
- Notion Database
- Airtable
- Slack / メール通知

将来的な送信先:

- DB 保存
- 管理画面
- 企業マイページ

## 7. アカウント設計

### 7.1 基本方針

アカウントは企業のみに発行する。学生アカウントは MVP では作らない。

初期実装では、企業ごとに 1 アカウントを発行する。企業内の複数担当者アカウントは将来拡張とする。

発行フロー:

1. 企業が問い合わせ
2. 運営が契約 / サブスク状態を確認
3. 運営が企業アカウントを手動発行
4. 企業担当者にログイン情報を送付
5. 企業がログインして会員限定エリアを閲覧

認証方式:

- メールアドレス + パスワード

### 7.2 権限種別

最小構成:

- `public`: 未ログイン
- `company_member`: サブスク登録済み企業
- `admin`: 運営管理者

将来拡張:

- `company_owner`: 企業内の管理者
- `company_staff`: 企業内の担当者
- `company_trial`: トライアル企業
- `suspended`: 契約停止中

### 7.3 アクセス制御

非会員が会員限定 URL にアクセスした場合:

- ログインページへリダイレクト
- 「このページは企業会員限定です」と表示
- 会員登録 / 問い合わせ CTA を設置

契約停止中の企業がアクセスした場合:

- 詳細閲覧を停止
- 契約更新 / 運営問い合わせ導線を表示

会員ステータスは初期実装から導入する。

閲覧可能:

- `active`: 契約中
- `trial`: トライアル中

閲覧不可:

- `past_due`: 支払い確認待ち
- `suspended`: 停止中
- `cancelled`: 解約済み

## 9. 推奨技術構成

### 9.1 MVP 推奨

現在の静的サイトを活かしながら、まずは以下の段階で進める。

Phase 1:

- 静的な学生一覧 teaser ページを追加
- 非会員向け UI と CTA を実装
- 面談リクエストは未実装、または問い合わせに誘導

Phase 2:

- Next.js へ移行
- 企業ログインを追加
- 学生データを DB 管理
- 会員限定詳細ページを実装

Phase 3:

- 管理画面
- 閲覧履歴
- 企業ごとのお気に入り
- 面談リクエスト管理

### 9.2 本実装推奨スタック

- フロントエンド: Next.js
- 認証: Supabase Auth
- DB: Supabase Postgres
- DB アクセス: Supabase JS / `@supabase/ssr`
- デプロイ: Vercel
- フォーム通知: Resend / Slack Webhook / Google Form 連携

現在の Vercel 運用と相性が良いため、Next.js + Vercel + Supabase で進める。

## 10. UI 設計方針

### 10.1 一覧で「気になる」を作る

一覧ページでは、学生の全情報を読ませるのではなく、短時間で比較できる UI にする。

重要な見せ方:

- 動画を最初に見せる
- 学部・属性・志望業界をタグで見せる
- 価値観や深掘りはロック表示で存在だけ示す
- カードごとに「続きを見る」導線を置く

### 10.2 詳細で「会いたい」に変える

詳細ページでは、企業が面談リクエストの判断をしやすい情報構造にする。

推奨セクション:

- 動画 / 基本情報
- この学生の特徴
- 志望業界と理由
- 価値観・意思決定の軸
- 将来像
- 深掘り Q&A
- 面談リクエスト

### 10.3 企業向け UI のトーン

現在のサイトは若さ、勢い、熱量がある。一方で会員限定エリアは企業が継続利用する業務画面になるため、以下を意識する。

- 一覧は比較しやすく、情報密度を高める
- 詳細は読みやすく、判断材料を整理する
- CTA は派手にしすぎず、明確にする
- ロック表示は煽りすぎず、上品に期待を作る

## 11. セキュリティ・個人情報方針

学生データベースは個人情報を扱うため、公開範囲を明確に分ける。

必須方針:

- 学生本人の掲載同意を取得する
- 公開範囲を学生本人に明示する
- 一般公開と会員限定の情報を分離する
- 非会員に詳細情報を HTML 内で埋め込まない
- フロント側のぼかしだけで情報を隠した扱いにしない
- 企業が学生に直接連絡できる設計は初期では避ける
- 面談リクエストは運営経由にする

注意:

静的 HTML に詳細情報を書き込んで CSS でぼかすだけでは、ソースを見れば内容が読めてしまう。そのため、本実装ではサーバー側で認証済み企業にだけ詳細データを返す必要がある。

## 15. 結論

この機能は、近世 KINSEI の協賛・スポンサー導線を「応援」から「採用接点の創出」へ拡張する重要機能になる。

ただし、学生の個人情報を扱うため、単純な静的ページ追加ではなく、公開情報と会員限定情報を明確に分ける設計が必要。

最初は `students.html` による公開 teaser で企業の関心を測り、次に Next.js + 認証 + DB を導入して、本格的な会員限定データベースへ移行する進め方が現実的である。

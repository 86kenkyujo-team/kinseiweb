## 2. TOPページ メインビジュアル

### 実装方針

トップページ全体は企業向け寄りに調整する。ファーストビューでは「実績ある学生と出会える」ことを最初に伝える。

### 掲載仕様

- メインコピー: `学歴ではなく実歴で戦え`
- サブコピー: `実戦経験を積んだ学生と企業をつなぎ、採用市場のミスマッチを減らす`
- ファーストビューの補助訴求: `実績ある学生と出会える`
- 既存の `学生の挑戦が、企業の成長につながる。` と `学びと実践で、未来のキャリアをつくる。` は置き換える。
- OGP / meta description も、学生寄りの表現から企業向けの出会い・ミスマッチ削減の表現へ寄せる。

### CTA仕様

- Primary: `公開中の学生DBを見る` -> `/students`
- Secondary: `導入の相談をする` -> 企業向け相談フォーム、未用意なら暫定で `mailto:info@kinsei-career.jp`
- Header CTA: `学生DBを見る` -> `/students`
- Login CTA: `企業ログイン` -> `/login?next=/members/students`

### 確認事項

- `実歴` の表記で確定するか。現在の既存文脈では `実績` も多いため、見出しはヒアリング通り `実歴`、説明文では `実績` を使う想定。

## 3. TOPページ 数値実績

### 現状

- 登録学生数: 300+
- 参画企業数: 50+
- 掲載プロジェクト数: 24件
- 長期 16件 / 短期 8件

### 実装方針

ヒアリングシートでは掲載数値が未入力のため、実数が確定するまで正確な数字は出さない。

### 推奨仕様

以下のどちらかで実装する。

1. 数値カードを一時削除する。
2. 数値を出さず、予定表記にする。

予定表記にする場合の案:

- 登録学生数: `順次公開予定`
- 掲載企業数: `掲載準備中`
- 掲載プロジェクト数: `順次公開予定`
- 補足: `掲載情報は確認が取れたものから公開します。`

### 確認事項

- 実数を出すか、予定表記にするか。
- 現在の `300+` `50+` `24件` は削除してよいか。

## 4. サービス利用の流れ

### 実装仕様

既存の学生向けプロジェクト参加フローを、ヒアリングシートの3ステップへ置き換える。

1. `無料登録`
   - 説明: `自分の現在地を知る`
2. `キャリア面談`
   - 説明: `ビジョンから逆算して進路を考える`
3. `企業紹介・イベント参加`
   - 説明: `納得できる意思決定をする`

### 追加ブロック

サービス利用の流れの下に、以下の思想フローを追加する。

見出し: `なぜ近世の学生は選ばれるのか？`

フロー:

- `ビジョンを描く`
- `実戦で磨く`
- `理想の企業と出会う`

### 確認事項

- この3ステップは学生向け説明に近いため、企業向けトップ内では「学生がどう育つか」を示す位置付けで掲載する。
- 企業向けには、隣接して「企業側の導入後の流れ」を追加するかどうかは未確定。

## 6. 協賛企業・ロゴ掲載

### 現状課題

- TOPに `PARTNER` `COMPANY` などの仮ロゴがある。
- 協賛企業一覧に `Enterprise Logo` `Company Logo` `⚪︎⚪︎⚪︎` が残っている。
- ヒアリングではロゴは「今はない」、許可は「確認中」。

### 実装方針

- 仮ロゴを本物の協賛企業のように見せない。
- ロゴ許可が取れるまでは、企業名だけ、または「掲載準備中」表示にする。
- 企業名は正式名称で掲載する。

### カテゴリ仕様

協賛企業ページは、現状のプラン別カテゴリから、ヒアリングシートの業界カテゴリへ変更する。

- `メーカー（自動車、電機、食品など）`
- `商社（総合・専門）`
- `IT・通信・ソフトウェア`
- `金融・証券・保険`
- `サービス・インフラ`
- `不動産・建設・物品賃貸`
- `広告・マスコミ・エンタメ`

### 表示仕様

- 企業名が未提供のカテゴリは空欄にせず、`掲載準備中` と表示する。
- ロゴがない企業カードはテキストカードにする。
- ロゴがある場合のみ画像表示する。
- ロゴ許可が確認中の企業は本番掲載しない。

### 確認事項

- 掲載する協賛企業の正式名称一覧。
- 各社のカテゴリ。
- ロゴ掲載許可の状態。
- ロゴ画像ファイルの提供有無。

## 7. 料金プランページ

### 現状

- 応援企業枠: 1万円 / 月
- 応援企業枠: 3万円 / 月
- 導入企業枠: 45万円
- カスタムプラン: 要相談

### 実装仕様

ヒアリングシートに合わせて、スポンサー料金ページを以下の料金構成へ変更する。

#### プラットフォーム利用料

1. `単月プラン`
   - 補足: `いつでも解約OK`
   - 料金: `月額 5,500円`

2. `年間プラン`
   - 補足: `1年縛り`
   - 料金: `月額 3,300円`
   - 訴求: `実質2ヶ月分おトク！`

#### 人材紹介料

- 項目名: `人材紹介料（採用成功報酬）`
- 料金: `¥1,000,000`

### 料金ページの情報設計

- ファーストビューは `企業向け料金プラン` に変更する。
- 既存の「近大生を応援するライトプラン」寄りの文脈は弱める。
- 「プラットフォーム利用料」と「採用成功報酬」を分けて見せる。
- CTAは `導入の相談をする` と `資料を受け取る` の2つに整理する。

### 要確認

`月額 3,300円` と `実質2ヶ月分おトク！` の計算が一致していない可能性がある。

- 単月 5,500円を12ヶ月利用: 66,000円
- 年間 3,300円を12ヶ月利用: 39,600円
- 差額: 26,400円

この差額は、単月換算で約4.8ヶ月分に近い。  
表記をそのまま使うか、割引訴求を変更するか確認が必要。

### 追加確認事項

- 税込 / 税別表記。
- 初期費用の有無。
- 成功報酬の発生条件。
- 返金・解約条件を掲載するか。

## 9. トップ検索タブ

### ヒアリング要望

検索すると実際の企業の募集要項などが出てきて、詳細を確認したい場合はログインを促す。

### 現状

- TOPに検索UIはある。
- 入力条件は検索処理に使われていない。
- `検索する` は `/students` へ遷移するだけ。
- 募集要項や案件を管理するDBは未実装。

### 実装案 A: 軽量対応

初回リリースでは、検索UIを「学生DBへの入口」として扱う。

- ボタン文言: `学生DBで探す`
- 遷移先: `/students`
- 条件入力は削除または装飾扱いにしない。

メリット:

- 実装範囲が小さい。
- 既存Next.js学生DBを活かせる。

デメリット:

- ヒアリング要望の「募集要項検索」までは満たさない。

### 実装案 B: 募集要項検索を実装

Supabaseに企業募集要項テーブルを追加し、検索結果ページを作る。

想定テーブル:

- `companies`: 既存企業管理を利用
- `opportunities`
  - `id`
  - `company_id`
  - `title`
  - `industry_category`
  - `job_type`
  - `description_public`
  - `description_member`
  - `work_style`
  - `duration`
  - `tags`
  - `publication_status`
  - `created_at`
  - `updated_at`

想定ページ:

- `/projects`: 公開検索結果
- `/projects/[projectId]`: 詳細ページ
- 未ログイン時は詳細の一部だけ表示し、`ログインして詳細を見る` を出す。
- ログイン済み有効企業には詳細を表示する。

メリット:

- ヒアリング要望を直接満たせる。

デメリット:

- DB設計、管理画面、RLS、詳細ページ、検索UIが必要になり、実装範囲が大きい。

### 推奨

まずは案Aで公開品質を整え、募集要項検索は第2フェーズとして案Bを実装する。
